# PERFORMANCE

Аудит загрузки и потребления ОЗУ. Разбор конкретных причин «игра иногда не грузится
с первого раза» и того, куда уходит память.

Замеры снимаются командой `TerrariaXDK.exe --selftest` (секция «Storage / memory report»),
поэтому любая регрессия видна как число, а не как ощущение.

---

## 1. Почему загрузка «иногда» ломалась

### 1.1. Текстуры создавались не в том потоке (главная причина)

FNA рисует через OpenGL, а контекст GL привязан к потоку, который его создал.
В проекте `SDL_GL_MakeCurrent` **не вызывается нигде** — контекст один раз делается
текущим на главном потоке и больше не перепривязывается.

При этом старый `Main.LoadingThread` (фоновый поток) делал:

```csharp
_sheetTiles.LoadContent(Content);    // создаёт Texture2D
_sheetSprites.LoadContent(Content);
WorldView.LoadContent(Content);
UI.LoadContent(Content);
```

Создание текстуры без текущего контекста — неопределённое поведение. На одних драйверах
оно «прощается», на других падает, на третьих молча возвращает пустую текстуру.
Отсюда ровно тот симптом, который наблюдался: иногда работает, иногда нет, результат
зависит от машины и таймингов.

Автор кода это уже подозревал — в файле была ветка «если Unix, то грузим всю графику
на главном потоке» с комментарием *«ALL graphics loading will be deferred to the MAIN
thread»*. Ветка касалась только ARM, а проблема общая.

**Исправлено.** Вся работа с GPU вынесена в `Main.LoadGpuContent()`, который вызывается
с главного потока. Фоновый поток теперь занимается только аудио (декодирование музыки
и звуков) — там GPU не нужен, поэтому распараллеливание осталось и сплэш не подвисает.
Отдельная Unix-ветка больше не нужна и удалена.

### 1.2. Гонка на сплэш-экране → NullReferenceException

Логотипы 2–4 загружались в фоновом потоке, а сплэш листается по таймеру и про поток
ничего не знает:

```csharp
X = ResolutionWidth - SplashTextures[SplashLogo].Width >> 1,   // мог быть null
```

На быстром SSD поток успевал, на SD-карте (Anbernic!) — нет. Результат — исключение
внутри `Draw`, то есть падение на старте.

**Исправлено.** Логотипы 2–4 грузятся сразу в `LoadContent` (это 3 КБ, 2 КБ и 13 КБ).
Плюс в `DrawSplash` добавлена защита: если текстуры нет, сплэш не разыменовывает null,
а показывает прогресс-бар и ждёт готовности.

### 1.3. Флаги готовности без `volatile`

`_loadingThreadComplete` и `_loadingProgress` писал фоновый поток, а читал главный.
Без `volatile` запись могла быть не видна: главный поток продолжал считать, что загрузка
не закончена, и ждал полный таймаут (120 с) либо начинал игру с полузагруженным контентом.

**Исправлено.** Оба поля (и `_loadingStatusText`) объявлены `volatile`.

### 1.4. `ContentManager` не был потокобезопасным

`Dictionary<string, object> loadedAssets` — обычный `Dictionary`. При одновременном
обращении из двух потоков он не «иногда врёт», а портит внутренние бакеты: поиск уходит
в бесконечный цикл или выдаёт ложное «ассет не найден». Это классический источник
загадочных зависаний на загрузке.

**Исправлено.** Доступ к `loadedAssets` и `disposableAssets` защищён `lock`. Загрузка
выполняется внутри блокировки: два потока не станут декодировать один и тот же ассет
(иначе первый экземпляр утекал бы).

## 2. Куда уходит ОЗУ

Замер на текущем `Content/` (249 МБ на диске):

| Категория | На диске | В памяти | Комментарий |
|---|---|---|---|
| Текстуры и изображения | 21.7 МБ | ~22 МБ | распаковываются в RGBA |
| Шрифты (оба набора) | 144.8 МБ | 47–97 МБ | грузится **один** набор |
| — из них `Fonts/HD` | 97.2 МБ | 97 МБ | только при 1080p |
| Звуки | 9.0 МБ | ~9 МБ | PCM после декодирования |
| Музыка (WAV) | 80.3 МБ | **80 МБ** | постоянно, весь сеанс |

Итого на 1080p: ~180 МБ только на шрифты + музыку. На Anbernic с 1 ГБ ОЗУ это заметно.

### 2.1. Музыка — самый дорогой пункт (80 МБ)

`MusicEntry.Initialize` делает `SoundEffect.FromStream(fileStream)`. `SoundEffect`
декодирует **весь** WAV в PCM и держит буфер в памяти до конца сеанса. 19 треков
по 3–8 МБ = ~80 МБ, которые заняты всегда, хотя играет один.

FNA умеет стримить: `MediaPlayer.Play(Song)` → `FAudio.XNA_PlaySong(path)` читает файл
потоком (stb_vorbis). Ограничение — **только OGG**. Сейчас в `Content/ExtMusic` лежат
исключительно `.wav`, поэтому стриминг не включается.

**Что нужно, чтобы выиграть 80 МБ:** конвертировать 19 треков в OGG (Vorbis q5,
неотличимо на слух для игровой музыки) и включить стриминг. Диск: +~20 МБ вместо
80 МБ, ОЗУ: ~0 вместо 80 МБ. Оригинальные WAV при этом можно оставить как фолбэк.

Статус: не сделано — требует изменения контента, см. `ROADMAP.md`.

### 2.2. Шрифты: 144 МБ на диске, но грузится один набор

`UI.LoadFonts` берёт либо `Fonts/`, либо `Fonts/HD/` (при 1080p) и добавляет `_PS3`
только к `big`, `small`, `small2`. То есть варианты `_PS3` и `_sc` — это отдельные
файлы «на всякий случай», и большинство из них не грузится никогда.

Это не утечка, а цена поддержки трёх разрешений и двух платформ в одном наборе.
Уменьшать можно только переупаковкой шрифтов в атласы меньшего размера — отдельная
задача, заметно рискованнее.

### 2.3. Что уже сделано по памяти

- Сплэш-текстуры освобождаются сразу после показа (`Dispose()` + `null`) — 5 штук,
  мелочь, но раньше они жили до выхода.
- Двойная загрузка шрифтов при сплитскрине осталась по замыслу (нужны два набора
  размеров), но теперь не пересекается с фоновым потоком.
- Один `GC.Collect()` перед загрузкой GPU-ресурсов и один после: убирает временные
  массивы декодеров из-под пиковой аллокации и снижает фрагментацию LOH.

## 3. Порядок загрузки сейчас

```
LoadContent (главный поток)
  ├─ сплэш 0..4 (мелкие текстуры)          ~0.1 с
  └─ запуск фонового потока (только аудио)

LoadingThread (фон)
  ├─ SoundManager: 19 треков → PCM          ~80 МБ
  └─ SfxInstancePool: ~300 инстансов        ленивые голоса, память по требованию

Update (главный поток, когда поток завершён)
  ├─ GC.Collect()
  ├─ LoadGpuContent(): тайлы, спрайты, WorldView, UI, CRC32
  ├─ GC.Collect()
  └─ InitializePostSplash()
```

`SfxInstancePool` создаёт `SoundEffectInstance` заранее, но FAudio-голос выделяется
только в `Play()`, поэтому 300 объектов дешёвы, пока звук не играет. Это проверено
по коду `SoundEffectInstance.Play()` — создание голоса ленивое.

## 4. Что ещё стоит проверить (не сделано)

- **Стриминг музыки** через OGG (см. 2.1) — единственный крупный выигрыш по ОЗУ.
- **`GCLatencyMode`** на время игры — меньше пауз сборщика, но требует замеров.
- **Пиковое ОЗУ при декодировании** текстур: `Texture2D.FromStream` держит и сжатые,
  и распакованные данные одновременно. Для больших атласов это временный, но заметный
  скачок; если станет проблемой — читать DDS напрямую без промежуточного `Color[]`.
- **Замер на реальном устройстве**: `--selftest` показывает размеры файлов, но не
  фактический RSS. На Anbernic стоит один раз снять `WorkingSet` после загрузки, чтобы
  иметь точку отсчёта.
