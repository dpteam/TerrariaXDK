# INPUT

Сравнение управления ПК-версии (`refs/T104C`, `refs/T1061C`) и текущего TerrariaXDK.
Здесь зафиксировано, что именно расходится и как это чинить.

Основа сравнения — `refs/T104C/Terraria/Player.cs::UpdatePlayer` (начало метода)
и `refs/T104C/Terraria/Main.cs` (обработка кликов UI).

---

## 1. Как устроено на ПК

Один раз за кадр читаются устройства, дальше `Player` работает с флагами:

```csharp
if (Main.mouseState.LeftButton  == ButtonState.Pressed && !mouseInterface) controlUseItem = true;
if (Main.mouseState.RightButton == ButtonState.Pressed && !mouseInterface) controlUseTile = true;
```

Ключевые элементы:

| Элемент | Смысл |
|---|---|
| `controlUseItem` | ЛКМ — применить предмет (атака, кирка, меч) |
| `controlUseTile` | ПКМ — поставить блок / взаимодействовать с тайлом |
| `mouseInterface` | курсор над UI; пока true, ЛКМ/ПКМ **не** стреляют и не строят |
| `mouseLeftRelease` / `mouseRightRelease` | «кнопка была отпущена в прошлом кадре» → правильная семантика клика |
| `tileTargetX/Y` | всегда `(mouse + screenPosition) / 16`, без эвристик |
| `D1..D0` | прямой выбор слота хотбара |
| колесо (инвентарь открыт) | прокрутка рецептов (`focusRecipe`) |
| колесо (инвентарь закрыт) | смена слота хотбара |
| `dropItemCheck()` | при `itemAnimation == 0 && itemTime == 0` |

`mouseInterface` выставляется в `DrawInterface`: как только курсор попадает на любой
элемент интерфейса, клик перестаёт быть игровым действием. Это то, что не даёт
«стрелять в инвентарь».

---

## 2. Как устроено у нас

Мы идём другим путём: `KeyboardMouseInput` собирает **синтетический `GamePadState`**
и подмешивает его к настоящему геймпаду. Консольная логика остаётся как есть.

| Консольный элемент | Что это | Наш маппинг мыши |
|---|---|---|
| `Buttons.RightTrigger` | `controlUseItem` | ЛКМ |
| `Buttons.B` | `controlUseTile` | ПКМ (только в меню!) |
| `BTN_GRAPPLE = Buttons.LeftTrigger` | `controlHook` (крюк) | **ПКМ в игре** |
| `Buttons.X` | `controlThrow` | `R` |
| `Buttons.Y` | инвентарь | `E` / `Tab` |
| `UsingSmartCursor` | сам выбирает цель | включён по умолчанию |

## 3. Найденные расхождения (и что уже исправлено)

### 3.1. ПКМ = крюк вместо установки блоков — критично

В игре правая кнопка уходила в `Buttons.LeftTrigger`, а это `BTN_GRAPPLE`.
То есть «поставить блок» правой кнопкой было невозможно: она цепляла крюк.
`controlUseTile` включался только от `Buttons.B`, то есть от клавиши `B`,
и только когда `MenuContext` был ложным.

**Исправлено.** ПКМ → `Buttons.B` (`controlUseTile`) во всех контекстах.
Крюк переехал на среднюю кнопку мыши и клавишу `V`.

### 3.2. Нет `mouseInterface` — клик в инвентаре применял предмет

Пока инвентарь открыт, ЛКМ продолжала уходить в `RightTrigger`, и персонаж махал
мечом/копал, хотя игрок целился в слот. На ПК это отсекает `mouseInterface`.

**Исправлено.** В инвентаре ЛКМ теперь работает как `A` (действие с предметом),
а не как «применить предмет». Плюс добавлено поле `Player.mouseInterface`,
которое выставляется при открытом инвентаре и блокирует игровые действия.

### 3.3. Нет прямого выбора слота мышью в инвентаре

ПК: наводишь на слот — он активен, клик — взять/положить. У нас курсор ходит
только кнопками (`inventoryItemX/Y`).

**Исправлено.** Наведение мыши на сетку слотов выставляет `inventoryItemX/Y`
по реальной геометрии (сетка 10×4 + ряды стрел/монет + слот мусора).

### 3.4. `Q` конфликтовал

На ПК `Q` — бросить предмет (`cThrowItem`). У нас `Q` был замаплен в `Back` (карта).

**Исправлено.** `Q` → бросить (как на ПК). Карта осталась на `M`.

### 3.5. Smart cursor против мыши

`UsingSmartCursor = true` по умолчанию: игра сама наводит на цель и игнорирует
позицию курсора. ПК такого не знает.

**Исправлено.** При переходе на мышь smart cursor выключается; включается обратно
клавишей `C` или геймпадом (`RightStick`).

### 3.6. Курсор «прилипал» к кнопкам меню

`CursorOverride` (флаг «управляет мышь») гас через 3 секунды простоя. В меню он не
включался заново, поэтому `UI.UpdateMouse` уходил в стиковую ветку и **переставлял
`MouseX/MouseY` на координаты пунктов меню** — визуально курсор прыгал к краям кнопок.
Тем же флагом гейтились обработчики мыши в выборе мира и режима игры, поэтому
«Начать игру» не нажималась, работал только пробел.

**Исправлено.** Пока меню открыто и мышь хотя бы раз использовалась, флаг удерживается
(`_mouseEngaged`). Активность геймпада сбрасывает его обратно — за геймпадом остаётся
приоритет, курсор игроку с контроллером не мешает.

### 3.7. `MenuContext` всегда был `true` — атака не работала

`CurMenuMode` присваивается только через `UI.SetMenu()` и **никогда не сбрасывается**
в `MenuMode.NONE` при старте игры: после входа в мир там остаётся последний экран.
Проверка «мы в меню» по нему всегда давала `true`, поэтому:

- ЛКМ всегда маппилась в `Buttons.A` («подтвердить»), а не в атаку;
- `Enter` всегда был «прыжок»;
- хотбар и быстрые действия (H/J/B) были отключены как «меню»;
- `Esc` всегда работал как «назад».

**Исправлено**: `MenuContext` определяется только по `CurMenuType` (MAIN/PAUSE = меню,
NONE = игра), плюс открытый инвентарь и диалоги. Это единственный надёжный признак.

### 3.8. Курсор двигался только в меню

`UpdateMouseAbsolute` делал `return` для случая «нет `uiCoords`» — то есть **в игре**.
В результате `Player.UpdateMouse` получал устаревшие `MouseX/MouseY`, и прицел
не следовал за мышью. Теперь позиция курсора просто копируется, а меню-специфичная
логика (выбор пункта под указателем) выполняется отдельно.

### 3.9. Двойной ввод в чате

Символы приходили двумя путями: `TextInputEXT` (SDL_TEXTINPUT) **и** собственный
fallback-обработчик `A..Z` по состоянию клавиш. Каждая буква печаталась дважды.
`Backspace` тоже обрабатывался в двух местах — удалял по два символа за нажатие.

**Исправлено**: единственный источник — `TextInputEXT` (включая `\b`, `\u007F`, `\r`).
Плюс `SuppressGameInput`: нажатие, которым закрывается чат, гасится до конца кадра,
иначе то же `Esc` тут же открывало паузу.

### 3.10. Esc срабатывал дважды; Tab дублировал инвентарь

В игре `Esc` открывает паузу по **отпусканию** (`IsButtonUntriggered(Start)`), а в меню
работает как «назад» по **нажатию** (`IsBackButtonTriggered`). Один цикл «нажал-отпустил»
успевал сделать два действия: закрыть меню нажатием и снова открыть его на отпускании.

**Исправлено**: `Esc` срабатывает один раз за нажатие (`_escapeLatched`); повторно
клавиша учитывается только после отпускания.

Раскладка разведена, чтобы не было пересечений:

| Действие | Было | Стало |
|---|---|---|
| Пауза / назад | `Esc` | `Esc` (без изменений) |
| Инвентарь | `E`, `Tab` | `E`, `I` |
| Карта | `M` | `Tab`, `M` |

`Tab` освободился от инвентаря и теперь открывает карту — то есть «меню» на `Esc`,
а карта на `Tab`, как и предполагалось.

### 3.11. Клик «застревал» между экранами

`Buttons.A` для меню формировался по **удержанию** ЛКМ. При переходе между экранами
(выбор мира → выбор режима) кнопка уже была нажата на прошлом экране, поэтому новый
экран получал готовое «подтверждение» и сразу запускал игру — меню хостинга
(`Play Online` / `Invite Only`) не успевало показаться.

**Исправлено**: подтверждение формируется по **фронту** нажатия
(`LeftClicked`), а не по удержанию.

### 3.12. Курсор «прилипал» на самом деле из-за отрисовки
`UI.DrawInventoryCursor` — консольный спрайт выделения — в конце делал:

```csharp
MouseX = (short)x;
MouseY = (short)y;
```

То есть **каждый кадр отрисовки** возвращал координаты курсора на позицию пункта меню.
Мышь физически двигала указатель, но следующий же кадр затирал `MouseX/MouseY`
обратно, и нарисованный курсор замирал на строке. Плюс этот спрайт рисовался вторым
курсором поверх настоящего.

**Исправлено**: при активной мыши `DrawInventoryCursor` не рисуется и не трогает
координаты. Отдельно `UpdateMouse` теперь отслеживает указатель на **всех** экранах,
включая карту и инвентарь (раньше требовался `uiCoords != null`, и на этих экранах
координаты вообще не обновлялись). Курсор рисуется поверх меню и инвентаря.

### 3.13. Клик в меню активировал не тот пункт

Выбор пункта под курсором шёл через `uiCoords` — одна точка на пункт, и брался
**ближайший** в радиусе 160 px. Клик же подтверждал текущее выделение. Поэтому клик
«в пустоту» рядом с пунктом активировал его, а клик по другому пункту мог ничего не
изменить: выделение оставалось там, где было.

**Исправлено**: `DrawMenu` запоминает реальные прямоугольники нарисованных пунктов,
наведение выбирает пункт по попаданию в прямоугольник, а клик вне списка
**поглощается** (`ClickOutsideMenuEntries`) вместо активации случайной строки.

### 3.14. Колесо мыши

**Исправлено.** Раньше колесо было замаплено на `LeftShoulder`/`RightShoulder` — то есть
на «сменить раздел инвентаря». В игре это случайно работало как листание хотбара (через
`Player`), а в инвентаре переключало раздел вместо рецептов, и отличить два намерения было
невозможно.

Теперь колесо отдаёт **дискретные шаги** (`ConsumeWheelSteps`), а не нажатие кнопки:

| Где | Что делает |
|---|---|
| в игре | листает хотбар (10 слотов, с переносом через край) |
| в инвентаре, раздел «Crafting», вкладка рецептов | листает рецепты текущей категории |
| в остальных местах | игнорируется, накопление ограничено ±10 шагов |

Одна «нотка» = 120 единиц XNA; дробные дельты (тачпады, трекпады) накапливаются, поэтому
мелкий скролл тоже доходит до списка. Арифметика индексов вынесена в `WheelNav` и покрыта
тестом `wheel scrolling`.

### 3.15. Перетаскивание в инвентаре

**Сделано.** С открытым инвентарём:

- **ЛКМ** — взять/положить (тот же путь, что `Buttons.A` в консольной версии);
- наведение мыши перемещает курсор слота по сетке 10×4;
- **ПКМ** — разделить стек (в инвентаре мапится в `RightTrigger`, а не в «назад»);
- клик вне сетки ничего не делает;
- `Esc` / `Tab` — закрыть инвентарь.

Важная деталь: в mouse-режиме `UpdateInventory()` **не вызывался вообще**, поэтому клик
по слоту не срабатывал. Теперь порядок такой: `UpdateInventoryMenu()` (секции и таймеры)
→ наведение → `UpdateInventory()` только если курсор над слотом.

Не сделано: Shift-клик «быстрый перенос» (нужно выбирать целевую секцию).
Колесо при открытом инвентаре листает рецепты (см. 3.14).

### 3.16. Имена персонажа и мира

**Исправлено.** Раньше нажатие `Start` в создании персонажа сразу генерировало имя
вида `A3F19C07251015` и сохраняло персонажа — имя нельзя было выбрать вообще.
Теперь открывается виртуальная клавиатура (`NamePrompt`):

- поле предзаполнено тем же сгенерированным именем, так что «просто подтвердить» работает;
- своё имя можно набрать с клавиатуры или виртуальной клавиатуры;
- пустое имя и превышение длины отклоняются с объяснением, набранный текст сохраняется;
- `Esc`/`Back` — отмена: персонаж не создаётся (возврат в создание персонажа),
  мир не создаётся (возврат к выбору размера);
- управляющие символы и лишние пробелы вычищаются (`NameRules.Sanitize`) — иначе они
  попадали в файл сохранения и в строку roster'а.

**Куда возвращает создание персонажа.** Подтверждение имени и ответ «Yes» в
«Leave without creating a character?» возвращают **к списку персонажей**
(`UI.ReturnToCharacterSelect`). Раньше оба места вызывали `PrevMenu(-2)`, а параметр
`PrevMenu` — это абсолютная глубина истории, где отрицательное значение значит «на шаг
назад»: игрок оставался в редакторе персонажа, поэтому Yes выглядел нерабочим, а
сохранённый персонаж — невидимым. Отмена имени (`Esc`) по-прежнему возвращает в редактор.

**Как набирается текст.** Два источника, и это осознанно:

1. **`TextInputEXT` (SDL text input)** — правильный путь: раскладка ОС, мёртвые клавиши,
   IME. Включается при открытии клавиатуры (`StartTextInput`) и **перезапускается при
   каждом открытии**: раньше запуск делался один раз, ошибка проглатывалась, и до конца
   сессии буквы не приходили, хотя `Enter` и сетка работали.
2. **Резервный разбор нажатий** (`VirtualKeyboard.TypeFromKeys`, `KeyChar`) — если SDL не
   прислал ни одного символа за сессию, символы берутся из нажатий клавиш (US-раскладка,
   Shift учитывается, `Backspace`/`Delete` удаляют). Как только SDL хотя бы раз прислал
   символ, резервный путь выключается навсегда — так двойного ввода не бывает.

Сетка клавиатуры: `D-Pad`/стрелки двигают подсветку, `A`/клик нажимают клетку, `X` удаляет,
`Y` переключает страницу символов, `Enter`/`Start` подтверждают, `Esc`/`Back` отменяют.
Клик по клетке и её отрисовка считаются одной функцией (`CellRect`), иначе промах на
пиксель отправлял бы не ту букву. Нижний ряд — шесть клеток (пробел, del, caps, OK, X):
курсор обязан доставать до каждой нарисованной, иначе кнопка видна, но не нажимается.

При закрытии клавиатуры в лог (`Program.LogDebug`, категория `VirtualKeyboard`) пишется
строка вида `closed: 12 char(s) from text input, 0 from key edges, started=True
delivered=True` — по ней сразу видно, каким путём пришёл текст. Это и есть ответ на
«почему не печатается».

Лимиты: 16 символов для персонажа, 20 для мира — по ширине колонок в списках.

| Что | ПК | У нас | Комментарий |
|---|---|---|---|
| Имена персонажа/мира | ввод с клавиатуры | ввод (клавиатура или виртуальная) | по умолчанию подставляется сгенерированное имя |
| `F` | — | полный экран | конфликт, если понадобится бинд |

## 4. Переназначение клавиш

**Сделано.** `Настройки → Keyboard bindings` (MenuMode.KEYBINDS). Экран показывает все
действия и текущие клавиши; клик или `Space` начинает захват, следующее нажатие
назначается. `R` сбрасывает всё, `Esc` выходит.

- Значения хранятся в `Settings.ini`, секция `[Keys]`, ключ = имя действия
  (`Jump=Space`, `Inventory=E`, …). Файл пишется целиком, поэтому документирует
  и значения по умолчанию.
- Повторное назначение **занятой** клавиши запрещено — иначе два действия молча
  перестают работать. При попытке показывается «`<key>` is already used».
- `KeyBindings` — единственный источник клавиш: `KeyboardMouseInput`, `ChatInput`
  и быстрые действия берут ключи оттуда, а не из констант.
- `[Keys]` читается при старте (`KeyBindings.Load`) и сохраняется сразу после
  изменения (`KeyBindScreen.Persist`), чтобы падение не потеряло биндинг.

## 5. Порядок дальнейших работ

1. **Перетаскивание предметов мышью** (`mouseItem`, ПКМ = половина стека,
   Shift-клик = быстрый перенос).
2. **Колесо = рецепты** при открытом инвентаре.
3. **Переназначение клавиш** с сохранением в `Storage/Config` (см. `IDEAS.md`).
4. **Виртуальная клавиатура** для имён (и/или прямой ввод на десктопе).

## 5. Правило

Любое изменение управления проверяется по двум критериям:

1. геймпад продолжает работать ровно как раньше;
2. поведение сравнивается с `refs/T104C`, а не придумывается заново.

Если поведение сознательно отличается от ПК — это фиксируется здесь, в таблице 3.8.
