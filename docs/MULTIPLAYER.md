# MULTIPLAYER

Как устроен встроенный мультиплеер TerrariaXDK: без отдельного серверного EXE,
хост живёт внутри игрового процесса.

---

## 1. Почему пришлось переделывать

Консольная версия ходила через `Microsoft.Xna.Framework.Net.NetworkSession` — обёртку над
Xbox Live. В порте эта обёртка осталась, но `SignedInGamer`/`GamerServices` — заглушки:
`UI.HasOnline()` всегда возвращал `false`, `CanPlayOnline()` тоже, поэтому сетевые пункты
меню были недоступны.

ПК-версия (`refs/T111M`) устроена иначе: `Netplay` c `TcpListener`/`TcpClient`, плюс
**отдельный** `TerrariaServer.exe` (`ProgramServer.cs`). Нам нужен был третий путь:
логика ПК-версии, но сервер — внутри игры.

---

## 2. Слои

```
игровой код (NetMessage, Netplay, Main.UpdateClient/UpdateServer)
        │  умеет только это API
        ▼
NetworkSession            (Microsoft.Xna.Framework.Net)
        │  выбор транспорта
        ▼
IPeerTransport
     ├── TcpPeer       ← новый, по умолчанию
     └── MonoGamerPeer ← старый Lidgren, fallback
```

Ключевая идея: **`NetworkSession` остаётся нетронутым API**, меняется только транспорт.
Игровой код по-прежнему пишет `Netplay.gamer.SendData(packet, options, gamer)`,
а куда это уйдёт — TCP или Lidgren — решает `NetworkConfig.UseTcpTransport`.

### Почему интерфейс, а не переписывание

`NetMessage.cs` (75 КБ) и `Netplay.cs` содержат всю игровую сериализацию (packet id,
компактные целые, секции тайлов). Переписывать их — значит сломать совместимость
с уже работающими сценариями. Транспорт — самая изолированная часть, поэтому менялся
только он.

---

## 3. Протокол

Один TCP-порт (`[Network] Port`, по умолчанию 7777). Каждый кадр:

```
[int32 length][byte opcode][payload ...]
```

`length` — длина тела (opcode + payload), little-endian.
Верхняя граница — 4 МБ (`WireFormat.MaxFrameSize`), чтобы битый заголовок
не приводил к гигантскому выделению памяти.

| Opcode | Имя | Payload | Кто шлёт |
|---|---|---|---|
| 1 | `Hello` | `int32 protocol`, `string gamertag`, `string modSignature`, `string password` | клиент → хост |
| 2 | `Welcome` | `int64 assignedId` | хост → клиент |
| 3 | `Roster` | `int32 count`, затем `(int64 id, string tag)*` | хост → клиент |
| 4 | `Data` | сырой пакет игры (`NetMessage`) | обе стороны |
| 5 | `Join` | `int64 id`, `string tag` | хост → остальные |
| 6 | `Leave` | `int64 id` | хост → остальные |
| 7 | `State` | `int32 NetworkSessionState` | хост → клиент |
| 8 | `RosterRequest` | — | зарезервировано |
| 9 | `Reject` | `string reason` | хост → клиент |
| 10 | `Ping` | `int64 tick` | клиент → хост |
| 11 | `Pong` | эхо `Ping` | хост → клиент |

### Пинг

Клиент раз в секунду шлёт `Ping` с отметкой `Environment.TickCount`. Хост отвечает
`Pong` **сразу из транспортного потока**, не дожидаясь игрового кадра, — иначе замер
показывал бы ещё и частоту кадров. Клиент считает RTT и сглаживает его (3/4 старое +
1/4 новое), чтобы одиночный всплеск не дёргал индикатор.

Результат виден в HUD при подключении: `ping 42 ms   up 12.3 kbps   down 48.1 kbps`,
цвет меняется на жёлтый после 150 мс и на красный после 300 мс.

Строки — `BinaryWriter.Write(string)` (7-bit length prefix + UTF-8).

### Handshake

1. Клиент подключается, шлёт `Hello` с `ProtocolVersion`, подписью модов и паролем.
2. Хост проверяет версию протокола, подпись (`ModLoader.IsCompatible`) и пароль.
   Несовпадение → кадр `Reject` с причиной, соединение закрывается; клиент показывает
   «Connection refused: …» и завершает сессию.
3. Хост выдаёт `Welcome` с id клиента.
4. Хост шлёт `State` — чтобы поздний подключившийся сразу знал, идёт ли игра.
5. Хост шлёт `Roster` — кто уже в игре.
6. Хост рассылает остальным `Join` и добавляет геймера в сессию.

### Relay

Хост — звезда: клиентский трафик идёт на хост, хост раздаёт остальным.
`TcpPeer.ReceiveLoop` после обработки кадра вызывает `Broadcast(frame, except: sender)`.
Это упрощает NAT (нужен проброс только у хоста) и повторяет модель ПК-версии.

## 4. Потоки

Правило из `AGENTS.md`: игровая логика — один поток.

- Фоновые потоки (`AcceptLoop`, `ReceiveLoop`, `ClientLoop`, `DiscoveryLoop`)
  **не трогают** `Main`, `UI`, мир и игроков. Они только:
  - читают байты и разбирают кадры;
  - кладут `Action` в `ConcurrentQueue<Action> _inbox`.
- `TcpPeer.Drain()` вызывается из `NetworkSession.Update()` на игровом потоке и
  применяет все накопленные действия: `AddRemoteGamer`, `RemoveRemoteGamer`,
  `EnqueueIncomingPacket`, `ApplyRemoteSessionState`.

Отправка синхронная и защищена `lock (stream)` в `WireFormat.WriteAll` — очередей
на отправку нет намеренно: `NetMessage.SendMessage()` и так вызывается из игрового
потока, а блокирующая запись упрощает порядок доставки.

### Локальные игроки (split-screen)

`LocalNetworkGamer.SendData` изменился: пакет больше не кладётся в
`NetworkEvent.PacketSend` для всех подряд (это было для Lidgren-модели).
Теперь:

- локальные геймеры → `Session.SendNetworkEvent(PacketSend)` (замыкание в процессе);
- удалённые → `Session.SendPacketToAll` / `SendPacket` → `IPeerTransport`.

Так split-screen продолжает работать, а удалённые игроки получают данные по сети.

## 5. Отличие от `refs/T111M`

| | `refs/T111M` (ПК) | TerrariaXDK |
|---|---|---|
| Хост | отдельный `TerrariaServer.exe` | внутри игрового процесса |
| Транспорт | TCP + собственный `messageBuffer` | TCP + `IPeerTransport` поверх `NetworkSession` |
| Формат | собственный `NetMessage` ПК-версии (другие id) | консольный `NetMessage` (несовместим с ПК) |
| Секции мира | 200×150 тайлов | 40×30 тайлов (`NetClient.TileSectionsTaken`) |
| Игроков | 255 | 8 (`Main.PlayerSet`) |

**Совместимости с ПК-серверами нет и не планируется** — разные packet id и разные
размеры секций. Это отдельная задача из `ROADMAP.md` (этап 6), если понадобится.

## 6. LAN-дискавери

UDP на `[Network] DiscoveryPort` (по умолчанию 7778).

- Хост **слушает именно `DiscoveryPort`**. Раньше он биндился на произвольный
  эфемерный порт, поэтому запросы, отправленные на 7778, до него не доходили и
  хосты в локальной сети были невидимы в принципе. Если порт занят (второй
  экземпляр игры), дискавери отключается с записью в лог, а хостинг продолжает
  работать.
- Хост слушает широковещательные запросы длиной ≥4 байта с префиксом `TXDK`.
- Отвечает строкой: `TXDK|gamertag|players|freeSlots|modSignature|port|flags`.
  `flags` — необязательное поле (бит 0: нужен пароль), чтобы старые хосты
  оставались видимыми. `port` — реально занятый TCP-порт (при `Port=0` его
  выбирает ОС).
- Клиент (`TcpPeer.ParseDiscoveryReply`) разбирает ответ, ставит пометки «пароль» и
  «другие моды» и добавляет запись в `Netplay.availableSessions`. Раньше хосты с
  чужой подписью модов молча выбрасывались из списка — теперь они видны с пометкой,
  а отказ объясняет handshake.

Дополнительно `Netplay.DiscoverLanSessions()` подмешивает адрес из
`[Network] JoinAddress` (формат `host` или `host:port`) — ручное подключение,
когда broadcast не проходит (разные подсети, VPN).

## 7. Мастер-сервер и публичный список

LAN-дискавери видит только свою подсеть. Для игры через интернет есть мастер-сервер:
он хранит записи хостов и отдаёт их клиентам одним списком.

| Что | Где |
|---|---|
| Адрес по умолчанию | `[Network] MasterServer` = `play.dartpower.xyz:17777` |
| Резервные адреса | тот же ключ, через запятую: `a:17777,b:17777` |
| Публиковать свой мир | `[Network] PublishToMaster` (по умолчанию **выключено**) |
| Свой адрес в объявлении | `[Network] PublicAddress` (пусто = мастер берёт IP из соединения) |
| Кэш списка | `Storage/Cache/servers.json` |

### Протокол (HTTP/1.1 + JSON)

Мастеру не нужен наш код — только три endpoint'а, поэтому его можно держать на
любом хостинге с бэкендом на чём угодно.

```
GET  /v1/servers    -> {"servers":[{...}]}
POST /v1/announce   <- {"name","host","port","players","maxPlayers","version",
                        "passworded","worldName","motd","modSignature","platform"}
POST /v1/remove     <- {"host","port"}
```

Поля записи: `name` (имя мира), `host`, `port`, `players`, `maxPlayers`,
`version` (= `TcpPeer.ProtocolVersion`), `passworded`, `worldName`, `motd`,
`modSignature` (подпись набора модов), `platform`.

Мастер обязан выбрасывать запись, если от хоста не было `announce` дольше ~2 минут,
иначе список заполняется призраками. Если `host` в объявлении пустой, мастер
подставляет адрес, с которого пришёл запрос — это единственный корректный вариант
для домашнего подключения за NAT.

### Как это ведёт себя в игре

- Все обращения к мастеру идут **в фоновом потоке**, игра их не ждёт.
- Таймаут на запрос — 4 с (`MasterServerClient.TimeoutMs`).
- После неудачи — backoff 5 → 10 → … → 300 с; успех его сбрасывает.
- Не ответил ни один адрес — показываем LAN и кэш, без диалога ошибки.
- Ответ валидируется: не больше 512 КБ, битый JSON отбрасывается целиком,
  запись без валидного `host`/`port` пропускается.
- Хост объявляет себя сразу при старте и далее раз в 45 с; при выходе — `remove`
  (best effort, поток не блокирует закрытие мира).
- Список — это **подсказка**. Настоящая проверка всё равно в handshake:
  `ProtocolVersion` и подпись модов. Мёртвый сервер из списка отваливается по
  `ConnectTimeoutMs`, а не вешает игру.

## 8. Что ещё не сделано

- **Dedicated-хост.** Тот же `TcpPeer` без `Main`/графики: упирается в статический
  `Main` и загрузку контента, поэтому это отдельная большая задача.
- **Карточки серверов в списке.** Публичные и LAN-серверы уже в одном списке, но
  отрисовка не показывает пинг и версию.

## 9. Как это проверяется

`--selftest` содержит проверку `host and two clients`, которая поднимает настоящий
хост и двух настоящих клиентов на реальных сокетах (loopback) и прогоняет три
«игровых цикла»:

1. оба клиента подключаются, хост видит двоих в roster, клиенты видят хоста;
2. в roster приходят **реальные gamertag'и**, а не «Stub Gamer»;
3. пакет от клиента 1 доходит до клиента 2 через relay хоста, байт в байт, с
   отправителем; и наоборот;
4. выход клиента 2 замечается хостом (иначе в мире остаются призраки).

Имя, которое видят другие игроки, — `[Game] Gamertag`. По умолчанию оно берётся из
учётной записи ОС (`PlayerIdentity.Default`), потому что у консоли его давал Xbox Live, а
без этого все игроки назывались одинаково — `Terrarian`. Меняется в
**Настройки → Network → Player name**, применяется сразу (обновляются и настройка, и
`SignedInGamer`, из которого транспорт берёт имя в handshake).

Сессии создаются напрямую (`new NetworkSession(...)` + `StartHostPeer`/`StartClientPeer`),
а не через `NetworkSession.Create/Join`: те статические методы разрешают одну активную
сессию на процесс (`activeSession`), что для игры правильно, а для теста — нет.
Порт берётся как `0`, то есть свободный от ОС, чтобы тест не конфликтовал с запущенной
игрой и не зависел от 7777.
