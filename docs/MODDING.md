# MODDING

Как написать мод для TerrariaXDK. Моды работают и в сингле, и в онлайне.

---

## 1. Что такое мод

Мод — обычная .NET-библиотека (`net40`), которая лежит в портативной папке `Storage/`
рядом с игрой:

```
TerrariaXDK.exe
Storage/
  Mods/
    MyMod/
      MyMod.dll          <- сборка с классом-наследником Mod
      disabled.txt       <- опционально: папка игнорируется
      textures/...       <- ваши файлы (загружаются через ModContext)
```

Загрузчик обходит `Storage/Mods/*/`, берёт все `*.dll`, ищет классы, унаследованные от
`Terraria.Mods.Mod`, и создаёт по одному экземпляру каждого. Папки с `disabled.txt`
пропускаются.

Папка **без** `.dll`, но с `Item/*.ini` — это Raw Mod: тот же мод, только данные вместо кода,
и компилятор для него не нужен. Подробно — раздел 10a.

Путь можно узнать программно: `Terraria.Storage.AppPaths.Mods`.

---

## 2. Минимальный мод

```csharp
using Terraria;
using Terraria.Mods;

[assembly: ModInfo("MyMod", "1.0.0", "Ваше имя", "Что делает мод")]

namespace MyMod;

public class MyMod : Mod
{
	public override void Load()
	{
		Context.Log("загружен");
	}

	public override void OnGameUpdate()
	{
		// вызывается каждый кадр, пока идёт игра
	}

	public override void OnPlayerUpdate(Player player)
	{
		// вызывается для каждого активного игрока каждый кадр
	}
}
```

`ModInfo` — атрибут уровня сборки. Он определяет имя и версию в подписи набора модов,
поэтому **меняйте версию при изменении поведения** — иначе клиенты с разными версиями
вашего мода будут считаться совместимыми.

## 3. Хуки

| Хук | Когда вызывается | Что можно делать |
|---|---|---|
| `Load()` | один раз после загрузки контента игры | инициализация, чтение конфигов |
| `Unload()` | при выходе из мира / завершении | освобождение ресурсов |
| `OnGameUpdate()` | каждый кадр, до обновления UI | логика мода |
| `OnPlayerUpdate(Player)` | каждый кадр для каждого активного игрока | баффы, эффекты |
| `OnWorldLoaded()` | после загрузки/генерации мира | расстановка объектов |
| `OnWorldSaving()` | перед записью мира на диск | сериализация данных мода |
| `OnTilePlaced(x, y)` | поставлен тайл (не во время генерации) | реакция на строительство |
| `OnTileKilled(x, y)` | сломан тайл (не во время генерации) | дропы, счётчики, события |
| `OnNpcHurt(npc, dmg)` | NPC получил урон | `npc.Life <= 0` = убит этим ударом |
| `OnNpcSpawn(npc)` | NPC появился, уже инициализирован | пометить, изменить, посчитать |
| `OnNpcDeath(npc)` | NPC умер, ровно один раз | учёт убийств, счётчики |
| `OnPlayerHurt(player, dmg)` | игрок потерял здоровье | `dmg` — после защиты |
| `OnLiquidChanged(x, y)` | игрок изменил жидкость (ведро) | реакция на ведро |
| `OnPacket(byte[])` | пришёл пакет от другого игрока | сетевые данные мода (**фон. поток**) |

Порядок вызова — порядок загрузки: `Storage/Mods/loadorder.txt`, затем по имени папки.
Если два мода правят одно и то же, побеждает загруженный позже.

### События мира: чего в них нет

`OnTilePlaced` / `OnTileKilled` / `OnNpcHurt` / `OnNpcSpawn` / `OnNpcDeath` /
`OnPlayerHurt` / `OnLiquidChanged` вызываются **на главном потоке, прямо внутри игрового
кода** — внутри расстановки/ломания тайла, `NPC.StrikeNPC`, `NPC.CheckDead`, `Player.Hurt`.
Два следствия:

- **Держите их дешёвыми.** Никаких аллокаций и обходов мира: посчитайте и запомните,
  а настоящую работу сделайте в `OnGameUpdate`.
- **Во время генерации мира они молчат.** Генерация вызывает те же функции миллионы раз;
  хуки там превратили бы пару секунд в минуту.

`OnNpcDeath` — единственный способ узнать о смерти ровно один раз. `OnNpcHurt` срабатывает
на каждый удар, и мультиударное оружие прислало бы «убит» несколько раз на одну смерть.
Разница в том, что нужно:

| Задача | Где |
|---|---|
| изменить лут, снять эффект, «последний удар» | `OnNpcHurt`, пока `Life <= 0` и NPC ещё активен |
| посчитать убийства, один раз | `OnNpcDeath` (слот уже очищен, лут уже выпал) |

`OnLiquidChanged` — **только действие игрока** (ведро), не симуляция: естественное течение
трогает тысячи клеток за кадр, и хук на него был бы хуком на саму воду. Если моду нужно
«озеро утекает», пусть опрашивает свои тайлы в `OnGameUpdate`.

В мультиплеере `OnNpcHurt` / `OnNpcDeath` / `OnPlayerHurt` срабатывают на той стороне,
которая применила урон; прежде чем что-то менять, проверьте `Context.IsHost`.

## 4. ModContext

```csharp
Context.Name        // имя мода
Context.Directory   // абсолютный путь к папке мода
Context.LocalPlayer // игрок этой машины (null в меню)
Context.IsMultiplayer
Context.IsHost

Context.LoadTexture("textures/icon.png")   // PNG или DDS
Context.LoadSound("sounds/ping.wav")       // WAV
Context.ReadAllText("config.txt")
Context.Log("сообщение")

Context.SendPacket(bytes)   // отправить пакет остальным игрокам
Context.CanSendPackets      // есть ли соединение

Context.Item("Copper Shortsword")   // правка статов предмета, null если имени нет
```

`LoadTexture` возвращает `null`, если файла нет или он битый — обязательно проверяйте.
Ничего не грузится из `Content/` игры: мод полностью автономен.

### Правка статов предмета

```csharp
ItemOverride item = Context.Item("Copper Shortsword");
if (item != null)
{
    item.Damage = 12;
    item.UseTime = 17;
    item.AutoReuse = true;
}
```

Имя — то, которое видит игрок («Copper Shortsword»), а не id: id принадлежит контенту
этой сборки, а имя общее у автора мода и у файла сохранения. Правка не меняет живой
объект — она запоминается и применяется сразу после `Item.SetDefaults`, поэтому её видят
все копии предмета: в сундуке, в магазине, в инвентаре после загрузки.

Ручка **только для записи** намеренно: прочитать через неё можно было бы лишь саму правку,
а не предмет, и это другой вопрос с разным ответом для каждой копии.

Новых предметов так не создать: новый id ломает сохранения и сетевой протокол. Это
ограничение осознанное, см. раздел 6.

### Рецепты

`Context.AddRecipe` добавляет крафт:

```csharp
ModRecipe recipe = Context.AddRecipe("Copper Bulgeon");
if (recipe != null)
{
    recipe.Amount = 1;
    recipe.Category = Terraria.Recipe.Category.WEAPONS;
    recipe.AddIngredient("Copper Bar", 6);
    recipe.AddIngredient("Wood", 1);
    recipe.AddStation("Anvil");
}
```

- **Ингредиенты и станции — по имени**, и разрешаются **после** загрузки всех модов: ингредиентом
  может быть предмет другого мода, а у него нет id, пока все не загрузились.
- **Станции — фиксированная английская таблица** (`Work Bench`, `Anvil`, `Furnace`, `Hellforge`,
  `Bottle`, `Table`, `Chair`, `Demon Altar`, `Loom`, `Cooking Pot`, `Sawmill`,
  `Tinkerer's Workshop`, `Mythril Anvil`, …), а **не** `Main.TileNames`: тот массив
  перезаполняется `Lang.SetLang` на языке игрока, и немецкий клиент искал бы «Anvil» и находил
  «Amboss». Файлы данных пишутся по-английски.
- **`Workbench` и `Work Bench`** — оба принимаются: паки пишут по-разному.
- **Рецепт с неизвестным ингредиентом или станцией отклоняется** и попадает в лог с именем.
  Рецепт, который ничего не производит, хуже отсутствующего: он занимает место в списке крафта.
- **Категория** (вкладка крафта) выводится из полей предмета — догадка, и честная: tConfig её не
  указывает, а категория — это группировка в интерфейсе, а не механика. Ошибка ставит рецепт не
  в ту вкладку, что неприятно, но не ломает. Автор правит одну строку.

Почему это была отдельная работа: массив рецептов был фиксированным (`new Recipe[342]`), и
**все** циклы в нём говорили `342`. Мод-рецепт просто не мог попасть в игру. Теперь размер —
`Recipe.Capacity` (ванильные + запас для модов), а циклы идут до `Recipe.NumRecipes`.

### Новые предметы

`Context.DefineItem` создаёт предмет, которого в игре не было:

```csharp
ModItem sword = Context.DefineItem("Copper Bulgeon", "items/copper-bulgeon.png");
if (sword != null)
{
    sword.Damage = 6;
    sword.Width = 30;
    sword.Height = 30;
    sword.UseAnimation = 28;
    sword.UseSound = 1;
    sword.Knockback = 4.5f;
    sword.Melee = true;
    sword.MaxStack = 1;
}
```

Спрайт обязателен: PNG в папке мода. Предмет без картинки в инвентаре неотличим от бага, и
автор узнаёт об этом при загрузке, а не от игрока.

**Как это устроено, и почему именно так:**

- **Id выделяются после загрузки всех модов**, в порядке `(имя мода, имя предмета)`.
  Не в порядке регистрации: id едет по проводу, и два игрока с одинаковыми модами,
  загруженными в разном порядке, иначе разъехались бы — а выглядело бы это как «предмет
  превратился в другой».
- **Id — число выше ванильных** (`ModItems.IdBase` = 20000). Это единственный способ не
  сломать ни сохранения, ни протокол: `Item.Type` — `short`, и он уже ездит по сети.
  Цена: у обеих сторон должен быть мод — ровно для этого и существует требование
  совпадения набора модов.
- **Спрайты пакуются в одну текстуру на мод** при загрузке и кэшируются в
  `Storage/Cache/ModSheets/`. Одна текстура — потому что `SpriteBatch` сбрасывает пачку при
  её смене, и отдельные PNG на каждый предмет стоили бы по сбросу на предмет. Кэш — потому
  что распаковка сотни PNG на каждом запуске заметна, а меняется она только когда меняются
  файлы. Ключ кэша — имена, размеры и время правки, так что правка одного спрайта
  пересобирает только этот мод.
- **Если мод не загружен**, его id из сохранения становится **пустым слотом** с записью в
  лог. Не исключением и не «предметом с мусорными данными».

Что нового предмета **не** умеет: поведения из tConfig-кода (`OnUse`, `PreDraw`). Предмет —
это данные: статы, спрайт, звук, снаряд. Для оружия ближнего боя и брони этого достаточно;
«стреляет тремя снарядами по дуге» придётся писать кодом мода.

Проверка `mod items` покрывает выделение id, применение статов, имя, пустой слот для
потерянного мода и формат кэша спрайтов. Сама упаковка текстуры требует графического
устройства и в headless-тест не входит — она проверена вживую на 114 предметах
сконвертированного пака.

## 5. Онлайн

Моды работают и в мультиплеере, но с двумя правилами:

1. **Подпись набора.** `ModLoader` считает FNV-1a по отсортированному списку
   `имя|версия` всех загруженных модов. Эта подпись передаётся в handshake.
   Если у хоста `[Mods] RequireMatchingMods=True` (по умолчанию), клиент с другой
   подписью не подключится — в логе будет причина.
2. **Никаких читов.** `OnPlayerUpdate` вызывается на клиенте, поэтому не пытайтесь
   через мод менять то, что проверяет хост (урон, инвентарь, тайлы): в онлайне это
   либо не сработает, либо будет рассинхрон.

Если мод упал с исключением, он **отключается**, а игра продолжается:
исключение пишется в лог, остальные моды работают.

### Свои пакеты

У модов есть собственный канал — без регистрации id и без правок протокола игры:

```csharp
// отправка (клиент → хост, хост → всем остальным)
byte[] payload = new byte[] { 1, 2, 3 };
Context.SendPacket(payload);

// приём: пакет пришёл от мода с тем же именем на другой машине
public override void OnPacket(byte[] payload)
{
    // ЭТО ФОНОВЫЙ ПОТОК. Ничего не трогаем здесь, только складываем данные.
    _queue.Enqueue(payload);
}

public override void OnGameUpdate()
{
    while (_queue.Count > 0)
    {
        Apply(_queue.Dequeue());   // игровой поток, можно менять мир
    }
}
```

Почему так, а не через `NetMessage`: его id зафиксированы консольным протоколом, и
любой новый id сломал бы совместимость. Кадр мода — отдельный opcode транспорта
(`OpMod`), содержимое `[длина id][id][payload]`, хост пересылает его как обычные данные.

Ограничения: один пакет — до 64 КиБ (больше отклоняется с записью в лог, не режется),
отправка возможна только при живом соединении (`Context.CanSendPackets`).
Пакеты от мода, которого нет на этой стороне, отбрасываются с одной строкой в логе.

## 6. Ограничения текущего API

- События мира: есть тайлы и урон по NPC. Нет спавна NPC, смерти NPC отдельным
  событием, изменения жидкостей и урона по игроку — в планах.
- Новые предметы/NPC/снаряды не создаются: для них нужны новые id, а они ломают
  сохранения и сетевой протокол (см. раздел про tConfig).
- Нет изоляции в отдельный `AppDomain` — упавший мод отключается, но не выгружается.
- API не версионирован; считайте его нестабильным до версии 2 (см. `IDEAS.md`).

## 8. Меню модов в игре

`Настройки → Mods` — список папок из `Storage/Mods`:

- `[on]` / `[off]` — состояние, версия загруженного мода;
- **LMB** или **Space** — включить/выключить (создаёт или удаляет `disabled.txt`);
- **←/→** — порядок загрузки, см. ниже;
- **R** — пересканировать папку (например, после копирования нового мода);
- **Esc** — назад;
- снизу показываются подпись набора, число загруженных модов и число ошибок загрузки
  (подробности — в `terraria-debug.log`).

**Важно:** включение и выключение применяются **после перезапуска**. Загруженную
.NET-сборку нельзя выгрузить из процесса, поэтому «горячая» перезагрузка модов
невозможна — меню честно об этом пишет.

### Порядок загрузки

Порядок важен, когда два мода правят один и тот же предмет: **побеждает загруженный
последним**. Порядок хранится в `Storage/Mods/loadorder.txt`, построчно, сверху вниз:

```
# Mod load order, top to bottom. Later entries load last and win conflicts.
BaseTweaks
MoreOres
```

- Моды, которых нет в файле, грузятся **после** перечисленных, по алфавиту — неполный
  или устаревший файл ничего не ломает.
- Файла нет — все моды грузятся по алфавиту, как раньше.
- Строки, начинающиеся с `#`, и пустые строки игнорируются; лишние записи (папка
  удалена) тоже.
- В меню порядок меняется стрелками **←/→**; файл перезаписывается сразу, но применяется
  после перезапуска, как и включение/выключение.

## 10. tConfig: импорт старых модов

Положите папки старых мод-паков в `Storage/tConfig/` (структура как в tConfig):

```
Storage/tConfig/
  MyPack/
    Item/Copper Shortsword.ini     damage=12
    Item/...                       useTime=17
```

При старте `TConfigImporter` читает `Item/*.ini` и превращает строки в правки
существующих предметов:

- имя файла ищется через `Terraria/ItemLookup.cs` — обратную таблицу от `Lang.ItemName`
  (`Item.SetDefaults(name)` **не** поиск: это `switch` на две дюжины legacy-предметов);
- поддерживаемые поля перечислены **в одном месте** — `ItemOverrides.SupportedFields`. Здесь
  список не дублируется намеренно: копия разошлась с кодом один раз и полтора года врала
  (в ней не было `consumable`, `stack`, `color`, `noUseGraphic`);
- всё остальное **не игнорируется молча**: причина попадает в лог и в отчёт конвертации, и
  причина настоящая — «нужны мод-тайлы», «это имя снаряда, а таблицы для него нет», а не
  «не число»;
- неизвестное имя предмета — предупреждение в лог, импорт продолжается.

Что именно теряется из реальных паков и что из этого стоит починить — `IDEAS.md`, раздел 1e.

Ограничения, о которых честно стоит знать:

- **новые** предметы/нпс/снаряды не создаются этим путём: для новых предметов есть
  `DefineItem` (см. 1c), а NPC, тайлы, стены, баффы и снаряды — нет, и это граница сборки;
- поля, которым нет места в этой сборке (`createTileName`, `light`, слоты брони), помечаются
  как неподдерживаемые **с причиной**;
- **`setName` — это не имя предмета.** В tConfig это имя **сета брони**: он сравнивает три
  надетых куска и вызывает `SetBonus` — метод мода. Без кода мода сет-бонуса не существует,
  поэтому поле не переносится; переименовать предмет им нельзя (и не нужно);
- спрайты из tConfig не подхватываются — они лежали в его собственных форматах;
- **id живёт в одном байте.** `Ammo`, `UseAmmo`, `Shoot` и `BuffType` — `byte`, так их задал
  консольный протокол. Поэтому мод-предмет (id с 20000) нельзя указать ни патроном, ни
  снарядом: `(byte)20043` — это 75, то есть другой предмет. Такое значение **отклоняется с
  причиной**, а не заворачивается молча, и поле остаётся прежним. Для `buffType` граница ниже —
  `Buff.MaxNumBuffs` (41), потому что за ней у баффа нет ни имени, ни иконки. Это ограничение
  сборки, а не пака: расширить его — значит менять формат сохранения.

Порядок применения: папки из `Storage/tConfig/` читаются **до** загрузки модов, поэтому если
пак и мод трогают одно поле, побеждает мод. Пак — это унаследованная папка, которой нет ни в
списке модов, ни в подписи набора; мод — явный, версионированный и общий для всех, кто
играет.

### Превратить пак в настоящий мод

Папка в `Storage/tConfig/` — это не мод: у неё нет имени в списке модов, она не входит в
подпись набора, и хост не может её потребовать. Поэтому есть конвертер.

**Сначала о самом простом пути.** Если код не нужен (а он нужен далеко не всегда), паку
достаточно стать Raw Mod — это одна команда и никакого компилятора (раздел 10a):

```powershell
TerrariaXDK.exe --tconfig-raw Storage/tConfig/MyPack
```

Дальше — путь для тех, кто хочет дописывать поведение: проект с C#.

```powershell
TerrariaXDK.exe --tconfig-convert Storage/tConfig/MyPack
# или с явными путями:
TerrariaXDK.exe --tconfig-convert Storage/tConfig/MyPack --out Storage/ModSources/MyPack --name MyTuned
```

Он пишет в `Storage/ModSources/<Имя>/` три файла: `<Имя>.csproj`, `<Имя>.cs` и `README.md`.
Дальше это обычный проект:

```powershell
dotnet build Storage/ModSources/MyPack/MyPack.csproj
# скопировать bin/Debug/net40/MyPack.dll в Storage/Mods/MyPack/
```

Что важно знать про результат:

- **это не одноразовый экспорт**, а исходник: правьте, дописывайте хуки, держите в git;
- числа переносятся как вызовы `Context.Item(...)` (см. раздел 4), а не как текст INI —
  поэтому мод компилируется и участвует в подписи;
- всё, что перенести нельзя, **перечисляется в `README.md`**: неизвестные имена предметов и
  поля без эквивалента. Молча выброшенное поле выглядело бы как удачная конвертация;
- `HintPath` в `.csproj` указывает на тот `TerrariaXDK.exe`, который запустил конвертер.
  На другой машине его надо поправить — это написано и в самом проекте.

Проверка `tconfig convert` в `--selftest` сверяет, что каждому поддерживаемому полю
соответствует реально существующее свойство `ItemOverride`: переименование свойства иначе
дало бы проект, который просто не собирается.

### 10a. Raw Mod: мод без компиляции

Компилятор нужен не всегда. Почти всё, что говорит пак, — это данные: урон, время
использования, спрайт, рецепт. Для этого есть второй вид мода: **Raw Mod** — папка в
`Storage/Mods/`, которую игра читает напрямую.

```
Storage/Mods/My Pack/
  mod.ini                     [Mod] Name=, Version=, Author=   (необязательно)
  Item/Copper Bulgeon.ini     type=-1, damage=12, [Items] Copper Bar=6
  Item/Copper Bulgeon.png     спрайт рядом с ini
```

Формат — **тот же, что у tConfig**, поэтому пак можно положить в `Storage/Mods/` как есть,
ничего не переписывая. Разница только в том, что происходит дальше: `RawMod` читает файлы и
регистрирует данные в тех же реестрах, что и скомпилированный мод (`ModItems`,
`ItemOverrides`, `ModRecipes`). Дальше игра их не различает: те же id, та же упакованная
текстура, та же подпись набора.

| | Compiled Mod | Raw Mod |
|---|---|---|
| Что лежит | `<Имя>.dll` (+ данные и ассеты) | `Item/*.ini` + `*.png` |
| Что умеет | данные **и** поведение | только данные |
| Нужен ли компилятор | да, при сборке мода | нет |
| Участвует в подписи | `имя\|версия` | `имя\|версия\|raw:<хеш содержимого>` |

Правила, которые стоит знать:

- **`type=-1`** (или любое отрицательное число) — «это новый предмет». Файл без этого
  маркера, чьё имя не существует в сборке, тоже считается новым, если рядом лежит PNG:
  спрайт — доказательство, что автор имел в виду предмет, а не опечатался.
- **Новому предмету нужен спрайт.** Без PNG файл пропускается с причиной в лог: предмет,
  который нельзя нарисовать, выглядит как баг игры, а не как мод.
- **Файл с именем существующего предмета — это правка**, а не второй предмет. Она идёт через
  `ItemOverrides`, то есть применяется после `SetDefaults` ко всем копиям.
- **Рецепт** берётся из тех же секций, что у tConfig, **в обоих написаниях**, которые
  встречаются в реальных паках:
  ```ini
  [Items]                 [Recipe]
  Copper Bar=6            Items=6 Copper Bar, 2 Wood
  [Tiles]                 Tiles=Work Bench
  Anvil=true              Amount=1
  ```

  Второе (одна строка на список, количество перед именем) есть у `SonnyMod` и `Suggestions`;
  раньше оно молча пропускалось как «не поле предмета», и такие предметы существовали, но
  скрафтить их было нельзя. Неизвестная станция (мод-тайл, которого в сборке нет) **не
  отменяет рецепт** — станция отбрасывается, предмет остаётся добываемым, а причина пишется
  в лог.
- **Один битый файл не отменяет пак.** Причина попадает в `terraria-debug.log` с префиксом
  `[Raw]`, остальные файлы загружаются.
- **Подпись считается по содержимому**, а не по имени папки: два игрока с «Omnirs Weapons», у
  одного из которых поправлен урон, не должны соединиться и молча разойтись в числах.
  `disabled.txt` в хеш не входит — включение и выключение мода не меняет того, что в нём.
- **Чего Raw Mod не может:** поведения. `OnUse`, свой AI, свой рисунок — это код, и для него
  нужна сборка. Пак, который в tConfig использовал код, станет набором данных; чего именно
  не хватило, видно в логе.
- **Чего эта сборка не умеет вообще: мод-NPC, мод-тайлы, мод-стены, мод-баффы и
  мод-снаряды.** У реальных паков они есть (`NPC/` у `Omnir's Creatures` — 146 файлов,
  `Tiles/` у `SonnyMod` — 88), и раньше они **молча** не читались. Теперь загрузчик считает их
  и говорит об этом: строка `[Raw] <мод>: 146 file(s) in 'NPC' - this build cannot load that
  kind of content` в логе, а в меню модов у строки появляется `N file(s) unusable`. Это не
  ошибка пака — это граница сборки, и лучше её назвать, чем дать игроку решить, что мод сломан.

В меню модов такой пак помечен `[Raw]` и показывает, сколько предметов он даёт. Включается и
выключается как обычный мод (`disabled.txt`), участвует в порядке загрузки.

**Конвертация пака в Raw Mod.** Меню модов умеет писать Raw-мод прямо из пака: `C` (или
`Enter`, или клик) — папка `Storage/Mods/<Имя>/` с `mod.ini`, переписанными `Item/*.ini` и
спрайтами; `P` — проект с C# (как раньше). То же из командной строки:

```powershell
TerrariaXDK.exe --tconfig-raw Storage/tConfig/MyPack
# или с явными путями:
TerrariaXDK.exe --tconfig-raw Storage/tConfig/MyPack --out Storage/Mods/MyMod --name MyMod
```

Переписывание, а не копирование: в результат попадают только те поля, которые сборка понимает,
поэтому отчёт конвертации описывает **мод**, а не файл — что выброшено, перечислено в
`README.md` рядом с модом. Повторная конвертация чистит `Item/` от файлов, которых в паке уже
нет, но только если папку создал сам конвертер (в `mod.ini` есть строка-маркер).

## 11. Отладка

- Все сообщения загрузчика — с префиксом `[Mods]` в `terraria-debug.log`; у Raw Mod строки,
  которых не хватило для загрузки, помечены `[Raw]`.
- Ошибки загрузки доступны в `ModLoader.LoadErrors`.
- Быстрая проверка, что мод вообще виден:

```powershell
.\TerrariaXDK.exe --selftest
# в выводе: [Mods] Loaded <N> mod(s), signature <hash>
```

## 8. Чем это отличается от tConfig

В `refs/T1061M` и `refs/T111M` лежит **tConfig** — мод-лоадер ПК-версии. Идеи
(деф-хендлеры предметов/NPC/снарядов, хуки на игрока) взяты оттуда, но реализация
своя:

| | tConfig | TerrariaXDK |
|---|---|---|
| Формат мода | `.tconfig` + компиляция C# на лету | сборка .NET **или** папка `Item/*.ini` (Raw Mod) |
| Компилятор | `CSharpCodeProvider` внутри игры | для Raw Mod не нужен; для поведения мод собирается отдельно |
| Совместимость | только ПК-версия | только TerrariaXDK |
| Данные | двоичные блобы в сохранении | пока нет своей сериализации |

Тащить tConfig целиком было бы дороже, чем написать загрузчик под уже существующие
типы игры.
