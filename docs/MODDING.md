# MODDING

Как написать мод для TerrariaXDK. Моды работают и в сингле, и в онлайне.

---

## 1. Что такое мод

Мод — обычная .NET-библиотека (`net40`), которая лежит в портативной папке `Storage/`
рядом с игрой:

```
TerrariaXDK.exe
Storage/
  Mods/
    MyMod/
      MyMod.dll          <- сборка с классом-наследником Mod
      disabled.txt       <- опционально: папка игнорируется
      textures/...       <- ваши файлы (загружаются через ModContext)
```

Загрузчик обходит `Storage/Mods/*/`, берёт все `*.dll`, ищет классы, унаследованные от
`Terraria.Mods.Mod`, и создаёт по одному экземпляру каждого. Папки без `.dll`
и папки с `disabled.txt` пропускаются.

Путь можно узнать программно: `Terraria.Storage.AppPaths.Mods`.

---

## 2. Минимальный мод

```csharp
using Terraria;
using Terraria.Mods;

[assembly: ModInfo("MyMod", "1.0.0", "Ваше имя", "Что делает мод")]

namespace MyMod;

public class MyMod : Mod
{
	public override void Load()
	{
		Context.Log("загружен");
	}

	public override void OnGameUpdate()
	{
		// вызывается каждый кадр, пока идёт игра
	}

	public override void OnPlayerUpdate(Player player)
	{
		// вызывается для каждого активного игрока каждый кадр
	}
}
```

`ModInfo` — атрибут уровня сборки. Он определяет имя и версию в подписи набора модов,
поэтому **меняйте версию при изменении поведения** — иначе клиенты с разными версиями
вашего мода будут считаться совместимыми.

## 3. Хуки

| Хук | Когда вызывается | Что можно делать |
|---|---|---|
| `Load()` | один раз после загрузки контента игры | инициализация, чтение конфигов |
| `Unload()` | при выходе из мира / завершении | освобождение ресурсов |
| `OnGameUpdate()` | каждый кадр, до обновления UI | логика мода |
| `OnPlayerUpdate(Player)` | каждый кадр для каждого активного игрока | баффы, эффекты |
| `OnWorldLoaded()` | после загрузки/генерации мира | расстановка объектов |
| `OnWorldSaving()` | перед записью мира на диск | сериализация данных мода |
| `OnTilePlaced(x, y)` | поставлен тайл (не во время генерации) | реакция на строительство |
| `OnTileKilled(x, y)` | сломан тайл (не во время генерации) | дропы, счётчики, события |
| `OnNpcHurt(npc, dmg)` | NPC получил урон | `npc.Life <= 0` = убит этим ударом |
| `OnNpcSpawn(npc)` | NPC появился, уже инициализирован | пометить, изменить, посчитать |
| `OnNpcDeath(npc)` | NPC умер, ровно один раз | учёт убийств, счётчики |
| `OnPlayerHurt(player, dmg)` | игрок потерял здоровье | `dmg` — после защиты |
| `OnLiquidChanged(x, y)` | игрок изменил жидкость (ведро) | реакция на ведро |
| `OnPacket(byte[])` | пришёл пакет от другого игрока | сетевые данные мода (**фон. поток**) |

Порядок вызова — порядок загрузки: `Storage/Mods/loadorder.txt`, затем по имени папки.
Если два мода правят одно и то же, побеждает загруженный позже.

### События мира: чего в них нет

`OnTilePlaced` / `OnTileKilled` / `OnNpcHurt` / `OnNpcSpawn` / `OnNpcDeath` /
`OnPlayerHurt` / `OnLiquidChanged` вызываются **на главном потоке, прямо внутри игрового
кода** — внутри расстановки/ломания тайла, `NPC.StrikeNPC`, `NPC.CheckDead`, `Player.Hurt`.
Два следствия:

- **Держите их дешёвыми.** Никаких аллокаций и обходов мира: посчитайте и запомните,
  а настоящую работу сделайте в `OnGameUpdate`.
- **Во время генерации мира они молчат.** Генерация вызывает те же функции миллионы раз;
  хуки там превратили бы пару секунд в минуту.

`OnNpcDeath` — единственный способ узнать о смерти ровно один раз. `OnNpcHurt` срабатывает
на каждый удар, и мультиударное оружие прислало бы «убит» несколько раз на одну смерть.
Разница в том, что нужно:

| Задача | Где |
|---|---|
| изменить лут, снять эффект, «последний удар» | `OnNpcHurt`, пока `Life <= 0` и NPC ещё активен |
| посчитать убийства, один раз | `OnNpcDeath` (слот уже очищен, лут уже выпал) |

`OnLiquidChanged` — **только действие игрока** (ведро), не симуляция: естественное течение
трогает тысячи клеток за кадр, и хук на него был бы хуком на саму воду. Если моду нужно
«озеро утекает», пусть опрашивает свои тайлы в `OnGameUpdate`.

В мультиплеере `OnNpcHurt` / `OnNpcDeath` / `OnPlayerHurt` срабатывают на той стороне,
которая применила урон; прежде чем что-то менять, проверьте `Context.IsHost`.

## 4. ModContext

```csharp
Context.Name        // имя мода
Context.Directory   // абсолютный путь к папке мода
Context.LocalPlayer // игрок этой машины (null в меню)
Context.IsMultiplayer
Context.IsHost

Context.LoadTexture("textures/icon.png")   // PNG или DDS
Context.LoadSound("sounds/ping.wav")       // WAV
Context.ReadAllText("config.txt")
Context.Log("сообщение")

Context.SendPacket(bytes)   // отправить пакет остальным игрокам
Context.CanSendPackets      // есть ли соединение

Context.Item("Copper Shortsword")   // правка статов предмета, null если имени нет
```

`LoadTexture` возвращает `null`, если файла нет или он битый — обязательно проверяйте.
Ничего не грузится из `Content/` игры: мод полностью автономен.

### Правка статов предмета

```csharp
ItemOverride item = Context.Item("Copper Shortsword");
if (item != null)
{
    item.Damage = 12;
    item.UseTime = 17;
    item.AutoReuse = true;
}
```

Имя — то, которое видит игрок («Copper Shortsword»), а не id: id принадлежит контенту
этой сборки, а имя общее у автора мода и у файла сохранения. Правка не меняет живой
объект — она запоминается и применяется сразу после `Item.SetDefaults`, поэтому её видят
все копии предмета: в сундуке, в магазине, в инвентаре после загрузки.

Ручка **только для записи** намеренно: прочитать через неё можно было бы лишь саму правку,
а не предмет, и это другой вопрос с разным ответом для каждой копии.

Новых предметов так не создать: новый id ломает сохранения и сетевой протокол. Это
ограничение осознанное, см. раздел 6.

## 5. Онлайн

Моды работают и в мультиплеере, но с двумя правилами:

1. **Подпись набора.** `ModLoader` считает FNV-1a по отсортированному списку
   `имя|версия` всех загруженных модов. Эта подпись передаётся в handshake.
   Если у хоста `[Mods] RequireMatchingMods=True` (по умолчанию), клиент с другой
   подписью не подключится — в логе будет причина.
2. **Никаких читов.** `OnPlayerUpdate` вызывается на клиенте, поэтому не пытайтесь
   через мод менять то, что проверяет хост (урон, инвентарь, тайлы): в онлайне это
   либо не сработает, либо будет рассинхрон.

Если мод упал с исключением, он **отключается**, а игра продолжается:
исключение пишется в лог, остальные моды работают.

### Свои пакеты

У модов есть собственный канал — без регистрации id и без правок протокола игры:

```csharp
// отправка (клиент → хост, хост → всем остальным)
byte[] payload = new byte[] { 1, 2, 3 };
Context.SendPacket(payload);

// приём: пакет пришёл от мода с тем же именем на другой машине
public override void OnPacket(byte[] payload)
{
    // ЭТО ФОНОВЫЙ ПОТОК. Ничего не трогаем здесь, только складываем данные.
    _queue.Enqueue(payload);
}

public override void OnGameUpdate()
{
    while (_queue.Count > 0)
    {
        Apply(_queue.Dequeue());   // игровой поток, можно менять мир
    }
}
```

Почему так, а не через `NetMessage`: его id зафиксированы консольным протоколом, и
любой новый id сломал бы совместимость. Кадр мода — отдельный opcode транспорта
(`OpMod`), содержимое `[длина id][id][payload]`, хост пересылает его как обычные данные.

Ограничения: один пакет — до 64 КиБ (больше отклоняется с записью в лог, не режется),
отправка возможна только при живом соединении (`Context.CanSendPackets`).
Пакеты от мода, которого нет на этой стороне, отбрасываются с одной строкой в логе.

## 6. Ограничения текущего API

- События мира: есть тайлы и урон по NPC. Нет спавна NPC, смерти NPC отдельным
  событием, изменения жидкостей и урона по игроку — в планах.
- Новые предметы/NPC/снаряды не создаются: для них нужны новые id, а они ломают
  сохранения и сетевой протокол (см. раздел про tConfig).
- Нет изоляции в отдельный `AppDomain` — упавший мод отключается, но не выгружается.
- API не версионирован; считайте его нестабильным до версии 2 (см. `IDEAS.md`).

## 7. Готовый пример

В `Examples/ExampleMod` лежит рабочий мод-образец: он показывает все хуки
(`Load`, `Unload`, `OnGameUpdate`, `OnPlayerUpdate`, `OnWorldLoaded`, `OnWorldSaving`),
чтение файла через `ModContext` и вывод в чат через `Main.NewText`.

```powershell
dotnet build TerrariaXDK.csproj
dotnet build Examples/ExampleMod/ExampleMod.csproj
# затем скопировать DLL в Storage/Mods/ExampleMod/
```

Проверить, что загрузчик его видит:

```powershell
TerrariaXDK.exe --selftest
# -> mods loaded: 1, signature <не vanilla>
```

Подробности — в `Examples/ExampleMod/README.md`.

## 8. Меню модов в игре

`Настройки → Mods` — список папок из `Storage/Mods`:

- `[on]` / `[off]` — состояние, версия загруженного мода;
- **LMB** или **Space** — включить/выключить (создаёт или удаляет `disabled.txt`);
- **←/→** — порядок загрузки, см. ниже;
- **R** — пересканировать папку (например, после копирования нового мода);
- **Esc** — назад;
- снизу показываются подпись набора, число загруженных модов и число ошибок загрузки
  (подробности — в `terraria-debug.log`).

**Важно:** включение и выключение применяются **после перезапуска**. Загруженную
.NET-сборку нельзя выгрузить из процесса, поэтому «горячая» перезагрузка модов
невозможна — меню честно об этом пишет.

### Порядок загрузки

Порядок важен, когда два мода правят один и тот же предмет: **побеждает загруженный
последним**. Порядок хранится в `Storage/Mods/loadorder.txt`, построчно, сверху вниз:

```
# Mod load order, top to bottom. Later entries load last and win conflicts.
BaseTweaks
MoreOres
```

- Моды, которых нет в файле, грузятся **после** перечисленных, по алфавиту — неполный
  или устаревший файл ничего не ломает.
- Файла нет — все моды грузятся по алфавиту, как раньше.
- Строки, начинающиеся с `#`, и пустые строки игнорируются; лишние записи (папка
  удалена) тоже.
- В меню порядок меняется стрелками **←/→**; файл перезаписывается сразу, но применяется
  после перезапуска, как и включение/выключение.

## 10. tConfig: импорт старых модов

Положите папки старых мод-паков в `Storage/tConfig/` (структура как в tConfig):

```
Storage/tConfig/
  MyPack/
    Item/Copper Shortsword.ini     damage=12
    Item/...                       useTime=17
```

При старте `TConfigImporter` читает `Item/*.ini` и превращает строки в правки
существующих предметов:

- имя файла ищется тем же способом, что и в игре (`Item.SetDefaults(name)`);
- поддерживаются поля: `damage`, `defense`, `pick`, `axe`, `hammer`, `useAnimation`,
  `useTime`, `useSound`, `shoot`, `shootSpeed`, `knockBack`, `mana`, `healLife`,
  `healMana`, `buffType`, `buffTime`, `rare`, `value`, `maxStack`, `autoReuse`,
  `melee`, `magic`, `ranged`, `potion`, `accessory`, `noMelee`, `crit`;
- всё остальное **не игнорируется молча**, а пишется в лог как неподдерживаемое;
- неизвестное имя предмета — предупреждение в лог, импорт продолжается.

Ограничения, о которых честно стоит знать:

- **новые** предметы/нпс/снаряды не создаются: для этого нужны новые id, а они ломают
  сохранения и сетевой протокол. Импорт работает как «твик существующего»;
- поля, которых нет в консольной сборке (например `consumable`), помечаются как
  неподдерживаемые;
- спрайты из tConfig не подхватываются — они лежали в его собственных форматах.

Порядок применения: папки из `Storage/tConfig/` читаются **до** загрузки модов, поэтому если
пак и мод трогают одно поле, побеждает мод. Пак — это унаследованная папка, которой нет ни в
списке модов, ни в подписи набора; мод — явный, версионированный и общий для всех, кто
играет.

### Превратить пак в настоящий мод

Папка в `Storage/tConfig/` — это не мод: у неё нет имени в списке модов, она не входит в
подпись набора, и хост не может её потребовать. Поэтому есть конвертер:

```powershell
TerrariaXDK.exe --tconfig-convert Storage/tConfig/MyPack
# или с явными путями:
TerrariaXDK.exe --tconfig-convert Storage/tConfig/MyPack --out Storage/ModSources/MyPack --name MyTuned
```

Он пишет в `Storage/ModSources/<Имя>/` три файла: `<Имя>.csproj`, `<Имя>.cs` и `README.md`.
Дальше это обычный проект:

```powershell
dotnet build Storage/ModSources/MyPack/MyPack.csproj
# скопировать bin/Debug/net40/MyPack.dll в Storage/Mods/MyPack/
```

Что важно знать про результат:

- **это не одноразовый экспорт**, а исходник: правьте, дописывайте хуки, держите в git;
- числа переносятся как вызовы `Context.Item(...)` (см. раздел 4), а не как текст INI —
  поэтому мод компилируется и участвует в подписи;
- всё, что перенести нельзя, **перечисляется в `README.md`**: неизвестные имена предметов и
  поля без эквивалента. Молча выброшенное поле выглядело бы как удачная конвертация;
- `HintPath` в `.csproj` указывает на тот `TerrariaXDK.exe`, который запустил конвертер.
  На другой машине его надо поправить — это написано и в самом проекте.

Проверка `tconfig convert` в `--selftest` сверяет, что каждому поддерживаемому полю
соответствует реально существующее свойство `ItemOverride`: переименование свойства иначе
дало бы проект, который просто не собирается.

## 8. Чем это отличается от tConfig

В `refs/T1061M` и `refs/T111M` лежит **tConfig** — мод-лоадер ПК-версии. Идеи
(деф-хендлеры предметов/NPC/снарядов, хуки на игрока) взяты оттуда, но реализация
своя:

| | tConfig | TerrariaXDK |
|---|---|---|
| Формат мода | `.tconfig` + компиляция C# на лету | обычная .NET-сборка |
| Компилятор | `CSharpCodeProvider` внутри игры | не нужен, мод собирается отдельно |
| Совместимость | только ПК-версия | только TerrariaXDK |
| Данные | двоичные блобы в сохранении | пока нет своей сериализации |

Тащить tConfig целиком было бы дороже, чем написать загрузчик под уже существующие
типы игры.
